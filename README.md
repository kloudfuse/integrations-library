# Kloudfuse integrations library

Prebuilt dashboards and alert rules that a Kloudfuse instance installs from its
Integrations page. The instance's browser fetches a generated file from `dist/`
straight from this repo, so there is no server.

## Layout

```
integrations/<component>/<collector>/   one integration's source (edit these)
  metadata.json                          name, summary, collector, tags
  DESCRIPTION.md                         what it covers and how to set it up
  dashboards/<slug>.json                 one Grafana dashboard per file
  alerts/<group>.json                    one Grafana rule group per file
tags.json                                the tags an integration may use
dist/                                    generated by scripts/validate.py --write; never edit
  index.json                             the catalog the Integrations page lists
  <id>.json                              one integration, combined into a single file
scripts/validate.py                      CI check; --write cleans sources and regenerates dist/
```

An integration's id is `<component>-<collector>`, e.g. `aws-rds-cloud`, taken from its
folder. `collector` is one of:

| collector | data comes from |
|---|---|
| `otel` | the OpenTelemetry collector |
| `datadog` | the Datadog agent |
| `cloud` | a cloud provider's metrics (CloudWatch, Azure Monitor, Cloud Monitoring) |

Cloud integrations are split per service, one per metric namespace: `aws-rds`,
`aws-lambda`, `gcp-cloud-sql`.

## Source files

`metadata.json`:

```json
{
  "schemaVersion": 1,
  "name": "Amazon RDS",
  "summary": "One sentence shown in the catalog.",
  "collector": "cloud",
  "tags": ["aws", "database"]
}
```

- `collector` must match the folder. Every tag must be listed in `tags.json`.
- `DESCRIPTION.md` is Markdown shown on the integration's detail page, under its name and
  summary, so it starts at `## Setup` rather than repeating them.
- `dashboards/*.json` are Grafana dashboard JSON, as exported.
- `alerts/*.json` are Grafana rule groups (`name`, `interval`, `rules`) with rules in the
  **provisioning-export** shape (`title`, `condition`, `data`, `noDataState`,
  `execErrState`, `for`, `annotations`, `labels` directly on the rule). The ruler shape,
  with the rule nested under `grafana_alert`, is rejected. A group's name is its
  filename and must be the integration id or start with it, so groups from two
  integrations never collide in one folder.
- Datasources are referenced by the fixed Kloudfuse datasource UIDs (Prometheus
  `P09C4D52DEC9B98E6`, logs `P10239062BE9ED4EF`).

`--write` strips instance fields from the sources (`id`, `uid`, `version`, `__inputs` on
dashboards; `uid`, `id`, `orgId`, `folderUID`, `ruleGroup`, `updated`, `provenance` on
rules) and replaces `${DS_*}` datasource placeholders with those UIDs, so an export can be
dropped in as is.

## Adding or changing an integration

1. Edit or add files under `integrations/<component>/<collector>/`.
2. Run `python3 scripts/validate.py --write` and commit the sources and `dist/` together.
3. Upload the integration's `dist/<id>.json` on a test cluster's Integrations page and
   check the dashboards render and the alert rules evaluate.

CI runs `python -m unittest discover tests` and `python scripts/validate.py` on every push
and pull request, and fails when `dist/` doesn't match the sources.

## Installing without network access

A Kloudfuse instance that can't reach GitHub can still install an integration: open its
file in `dist/`, use **Download raw file**, and upload it on the Integrations page.

## Provenance

The initial content was copied once from `kloudfuse/artifacts`, with alert rules
translated from Grafana's ruler shape to the provisioning-export shape and the cloud
packages split per service. `artifacts` is not kept in sync.
